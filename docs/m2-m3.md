# M2/M3 isolated integration: supported behavior and exact remaining gap

This branch starts at deployed bounded product commit `354d52ac`.
All 11 product SHA-256 values remain identical; no product/core fix was needed
for the exercised supported paths. Only NativeSync tests, runner and factual
documentation are added. Production, host working trees and phone are untouched.

## M2 supported behavior

The temporary native Queue/Adapter/SourceSync/SourceCatalog and real HTTP/SQLite
chain exercises two exact topics: additions, edits, explicit message tombstones,
offline durable commits, dropped accepted response, identical-op replay, changed
payload refusal, conflict retention with healthy-topic progress and reopen.
Three real subprocesses exit after durable plan, accepted baseline operation or
durable local commit. Original device/space/cursor prefix and synthetic old
3-message/5-Journal completed-execution/v1 facts remain. These are synthetic
execution records, not new native AA/model runs.

`sourcePaused=true` intentionally does not freeze completed topics: the test
proves their committed operations may still synchronize. Disabling the existing
connection and reopening the actual runtime performs no Bridge transport and
retains the existing source fence/Outbox. It blocks approved Queue mutation/write
entrances, permits unrelated local changes and recovers the original operation
when re-enabled. It is not a global filesystem or server-Bearer write lock.

Out-of-scope owner config readers/history snapshots/plans/catalog/baseline/push
stay excluded. Reading the native config of an approved owner still enumerates
its topic IDs before filtering; this is not a claim that an approved config file
containing sibling identifiers was never read. Explicit outside native writes
remain local; they are not counted as SourceSync snapshot reads.

## M3 supported initial scope

An explicitly approved initial limited scope with two Agents and two topics per
Agent supports incremental discovery of those approved identities, late history,
renames, same topic/message IDs across owners, concurrent work, cross-Agent
conflict/offline isolation, exact topic deletion and restart. The actual mobile
router exposes only those topics to a synthetic readonly session. Unapproved
siblings and the third owner are not enrolled. Broad owner deletion remains
refused, preserving approved siblings and central task/history facts.

## BLOCKED: expansion of an already-bound production-like limited source

This is a missing transition capability, not a regression or authorization to
widen production. Existing same-source scope widening is rejected by persisted
scope pin; changing to a newly granted wider source is rejected by local
`SourceSync.verify` with SOURCE_BINDING_CHANGED. Even if bypassing that local
check, an actual source HTTP catalog publish encounters SOURCE_IDENTITY_COLLISION
because existing owner/topic rows have unique canonical source ownership.
The failed request rolls back; original state bytes, Journal, v1/job and existing
readonly phone scope remain. No state rewrite, second space or full-root fallback
is used. A separate required-upgrade probe genuinely fails; refusal tests do not
convert that missing capability into PASS.

The smallest safe next contract must explicitly define an additive handover from
the old source to a new immutable limited source: require matching original
device/space/root and complete, settled old receipts; preserve canonical topic
keys, Journal/op identity and old execution/config keys; preserve the old paired
phone's exact old-topic read authority without granting its token new topics;
make server ownership/permission retirement and client receipt adoption durable,
idempotent and recoverable across acceptance/reply loss. The current singleton
source binding and unique catalog cannot express that handover. Simply changing
grant JSON or state is unsafe. This sprint therefore does not invent a new
multi-source ledger, broad permissions framework or an unreviewed takeover path.

No production expansion is ready. The shortest next production gate is only M2
within the two existing topics after Jenn explicitly authorizes continuous
writes and a narrow zero-model native-message/edit/Outbox check. M3 requires the
explicit handover contract and its independent isolation evidence first.

## Reproduction

Use the cumulative source bundle and packaged public host fixtures/dependency
lock. Run tools/run_m2_m3.py under Node24 with a new output directory.
Supported assertions and the required failure are reported separately. Exit2 is
PARTIAL; any unexpected fixture/load/assertion failure returns1. Raw failed first
fixture attempts are kept in the external evidence, never substituted for the
real SOURCE_BINDING_CHANGED counterexample. Old C1/C2, phone and 43 tests are
historical accepted evidence and are not added to these new counts.
