# NativeSync 架构问题修复计划

日期：2026-10-31（America/Adak）。依据：[架构审查及四个已复现问题](architecture-review-20261031.md)。源码基线 `f2a9d1e97b7de945c94f495b7a84a44f40727881`，tree `d35a9917d84e223b50a9be74cd2170f1e0d9427d`。

当前仅完成计划，产品代码尚未修复。保留本地已有 README、接手记录和审查报告的修改，不重置工作区。

## 实施顺序和范围

|顺序|修复|主要改动面|完成标准|
|---|---|---|---|
|1 / P1|停止受理、排空和取消分离|ToolBox 插件入口、MobilePortal、ConversationExecution、groupTurn、附件／同步路由|停止受理后没有新任务／新外部写入；已派发工作可结束；超时保留未知事实|
|2 / P1|按话题隔离持久积压|Bridge Adapter、新的收件分页存储、localAttachment、SourceSync、诊断消费端|A 超过原1000条积压时 B 继续同步；退出／重开不丢事件、不跳游标|
|3 / P2|任务状态有界查询|服务端任务查询、桌面 executionStatus、PWA 对应任务读取|10001条历史仍能刷新；分页有界；未完成／待核对任务不会静默丢失|
|4 / P2|减少无变化持久化|Adapter pull、SourceSync.report、执行状态缓存|真正空闲不重写主状态；有游标／业务事实变化仍可靠提交|

按上述顺序串行实施。第2项改动面最大，先完成存储和迁移合同，再改投影调度；第4项放在其后，避免同时改动同一提交路径。每项形成可单独评审的代码和验证记录，最后做一次联合回归。四项都可在当前 Linux 隔离环境开发。

## 1. 生命周期：先封受理，再等待，最后才取消

实现目标：把“维护时不再接受新工作”与“主动取消已派发工作”区分开。保留宿主现有 beginDrain 接线作为同步设置屏障的入口；等待过程放在现有关闭链，不建立独立停机服务。

- 新手机消息／邀请、新上传、配对，以及配置发布、Source 转换、目录和同步等外部写请求，逐项列出停机行为，并在实际业务入口检查。屏障设置后拒绝新的受理／外部写请求，返回稳定的可重试错误；已经进入处理的请求按原提交边界结束。
- 同一 requestId 的已受理请求可以读取原回执；停机读回不能制造新执行、重新派发或依赖客户端生成新 requestId。需要补齐的持久意图沿既有恢复链处理。
- 停止启动新的任务和群聊后续步骤；已经派发的单聊请求／群步骤允许正常结束。尚未派发的 queued 工作保留原身份和快照，之后按既有恢复规则接续。
- beginDrain 不立即 abort 全部活动 controller。超时或明确取消时才进入取消流程；已经可能发生副作用的工作保留 review_required，不能改成“从未执行”。
- 排空观测覆盖本插件的外部请求、inFlight、当前群步骤、审批等待和原生任务／工具未结状态。计数来自已有状态；插件计数不宣称代表整个 ToolBox 宿主空闲。
- 检查宿主关闭 listener 的顺序对原生 loopback 执行的影响。优先插件内修复；如定向测试证明宿主顺序无法满足合同，再更新必要的最小通用接线和对应 compat 记录，不直接覆盖宿主整文件。

验收：原 messages 反例应变为拒绝且 Journal／execution 增量为0；覆盖邀请和其他写入口；覆盖并发进入屏障、已受理回执读回、单聊／群步骤完成、超时未知、关闭后重开。使用合成 endpoint，真实模型／工具／AA调用为0。

## 2. 收件积压：持久事件与内存工作集分开

计划采用现有 `.native-sync` 下的耐久分页文件，保存尚未物化的原始事件；Adapter state 只保留必要的引用／处理位置和既有业务状态。它是待处理接收记录，不取得 Journal 或 History 的事实裁决权，不先引入新数据库。

提交顺序必须明确：**写入不可变分页并确保持久 → 原子提交页引用与接收游标 → 按话题物化并耐久确认 → 回收已确认分页。** 页或游标提交失败时保留最后可证明的接收位置，重复读取按原 seq 去重。不能先移动游标再补落盘。

- 内存只装载有界的页／话题工作集；冲突话题的持久积压不再消耗全 Source 的1000条逻辑配额。调度按话题公平推进，保持同话题顺序和真实因果依赖。
- 保留 projectionRecovery、before／after revision、pending local commit、Outbox、acked、receipt 的证明关系。迁出 inbox 不能解除原本应保持的 History 写入栅栏。
- localAttachment 的启动栅栏、SourceSync.verify 的“已稳定”判断、Adapter 恢复／诊断和相关投影消费者都改为理解外置待处理事件；不能继续仅检查旧 `inbox.length`。
- **需要显式新状态版本。** v2 先校验和保全，将原 inbox／pending 事件可靠写入新存储，再原子采用新格式。切换前退出仍可按旧状态重试；切换后只允许理解新格式的代码继续。旧版必须拒绝读取，不能因看到空 inbox 而跳过已接收事件。
- 缺页、坏摘要、路径别名、权限或磁盘写入失败均保留状态并明确报错；不静默丢弃或重建空队列。磁盘空间耗尽时允许明确停止接收，本计划不承诺无限积压。

验收：原1001次冲突反例及更大合成积压下，B能物化，A全部事件／冲突保留；重复分页、同话题顺序与相关依赖不变。分别在写页、提交游标、History物化、确认、回收边界注入退出，重开结果一致；验证v2迁移、中途退出、旧版拒读、断网和磁盘失败。

新格式采用后不能靠恢复旧 state／旧数据库回退。未来安装包需重新列明格式兼容性和向前恢复方式，不能继续套用原10文件代码回退清单。

## 3. 任务查询：服务端和消费者采用同一分页合同

在现有执行表上增加有界查询，默认页量与最大页量在服务端强制限制；按实际 SQL 查询补必要索引。优先使用稳定的 keyset 游标，避免 offset 随新增任务漂移。

- 终态历史按稳定任务顺序分页；未完成／待核对任务有明确的独立查询或纳入规则，也须可分页，不用“永远全部返回”绕过容量限制。
- 游标绑定已授权话题与协议版本。以请求开始时的任务顺序上界隔离新插入项；分页期间状态可变时如实定义为各页观测，不冒称数据库级原子快照。新任务由后续刷新取得。
- 先筛选当前页，再装配 NativeTaskLinks／工具详情，避免取全表后在 JavaScript 中切片。保留按原执行身份读取详细结果的入口。
- 桌面和 PWA 分别处理分页、部分失败、旧缓存、分页失效和重新刷新。128条桌面缓存与字节预算继续有效；界面明确总数／分页／截断，不让“缓存有界”变成“待核对任务已消失”。
- 新客户端显式使用新增的版本／分页参数。旧接口保持已支持规模内的原字段和语义；超过安全预算时明确拒绝或要求升级，不能悄悄裁剪却声称完整返回。

验收：10001条以上合成历史成功获得首屏和后续页；页间新增任务、状态变化、同毫秒时间、未决旧任务、错误话题游标、重试和网络失败均有确定结果。服务端返回量与客户端缓存量都有界，读取不增加执行、Journal或模型请求。

## 4. 空写：先消除可证明的无变化提交，再测规模

- pull 没有事件且 nextSeq 未变化时，跳过主状态事务。若为空的授权过滤页但全局扫描游标前进，仍须按接收合同耐久提交。
- 收件存储、迁移、local commit、Outbox／ack、projectionRecovery 等真实事实变化保持原有耐久级别。不要把关键写入统一延迟到定时批处理。
- SourceSync.progress 按内容变化报告，另保留明确频率的低频心跳；同 scope 暂停、错误和恢复状态都可观察。连接失败用既有恢复路径，不制造虚假的新鲜状态。
- 状态投影内容相同时避免重复保存大缓存。内存“刚观察到”的时间与磁盘“最后持久观察到”的时间分别定义，不丢失离线陈旧标记。
- 对1千／1万条合成消息状态记录提交次数、序列化字节和耗时，作为后续是否需要增量持久化的依据；不先承诺性能阈值或迁入新数据库。

验收：原五轮空同步反例变为主状态0次写入；真实事件、过滤页游标前进、丢回执重开仍正确。progress在变化时及时报告、稳定时按心跳工作；缓存节流不影响错误／恢复投影。
