# 第三轮：外部架构意见的逐项验证

日期：2026-10-31。验证基线 `15a24802ff2ae94bae585a2bce1a1050d0a1b99e`，仍在独立实验分支。附件是待核对的意见，不构成重构、上线或生产数据修复授权。本轮只增加实验、证据与文档，没有修改 overlays 产品代码、packages 内核、数据库 schema 或同步协议。

## 判断

意见中的简化方向值得吸收，但四项“裁决”不能整体采纳。应撤回上一轮把隔离回执直接列为下一轮路线的建议；先处理已证实的服务端错误分类与存储校验问题。同时，不能把未经实现的 topic_seq、opId 消费幂等和“自动恢复到28ms”当作现成能力。

|断言|验证结果|
|---|---|
|服务端存储坏记录返回400不合理|成立。真实HTTP合成故障仍是400/BAD_REQUEST，应有服务端损坏错误类别；本轮未修复。|
|CHECK(json_valid)能挡非法JSON写入|成立，真实SQLite拒绝非法语法；需允许合法删除的NULL，并单独处理既存表迁移。|
|加CHECK就消除了存储损坏与同步缺口|不成立。语法有效但身份/摘要错误的内容能通过；CHECK不在普通SELECT时重新验证，也不恢复历史损坏。|
|每个Topic天然有topic_seq或parent_hash|与当前实现不符。Journal没有这些列，messageCausality是消息依赖身份，不是连续话题序号或完整哈希链。|
|按原opId重新提交就得到新journal_seq|当前接口不成立。同一请求返回原seq/replayed；改变请求却复用键会拒绝。|
|旧客户端按opId幂等接收修复记录|与当前实现不符。pull事件不带opId，客户端按消息身份与seq去重。|
|旧历史加新seq即可天然安全修复|反例成立：已收到v2的客户端随后收到以新seq追加的v1，会回退到v1；服务端messages仍为v2。|
|纯决策固有地慢约4倍|上一轮没有分离成本，不能据此推断。应纠正性能归因。|
|谓词分组可保留条件更新语义|本轮原型通过结果对照、六个守卫字段变化、跨组整体回滚及参数分块检查。尚未接入执行器。|
|K通常小于10、规划低于2ms、总计约28ms|不是已验证保证。本机当前实现未达到；见下表。|
|review_required没有人工出口|与当前实现不符。原会话HTTP解除暂停的真实故障路径已跑通。|
|AA需要从零增加恢复查询|与当前实现不符。已有原生provider/query/reconcile/result路径；通用工具不因此自动拥有探针。|
|生成器不宜无限扩成手写打包器|合理的工程判断；未发现当前四个生成产物已损坏。发布阶段统一组装值得采纳为后续方向。|

## 1. 最小服务端修复与重发布反例

在独立临时SQLite/loopback HTTP/AppData中，给已接受记录注入非法JSON，健康话题在后。pull返回400，客户端游标不变。恢复该行原有、已知正确字节，再用现有pull，两个话题均恢复同步。这个实验说明：**当前失败关闭的前提下，服务端修复可用，客户端不必为此先增加回执表**。它不解决修复期间健康话题的可用性，也不是生产修复脚本。

另一实验按当前CentralStore正常提交v1、v2，客户端确认v2；随后在临时库里故意绕过写入权威，把v1原Journal内容追加到新seq。客户端回退到v1。此操作是对意见中“旧版本原样重发布天然兼容”的负面对照，不是建议的修复。

如果要让健康话题在损坏期间继续前进，需要另行明确：损坏话题如何对客户端可见、完整性如何表示、版本和删除如何排序、修复事务在哪个崩溃点生效、旧客户端怎样安全处理。重发布可以作为候选，但必须证明这些条件，不能靠“零新协议”省略它们。隔离回执同样只是候选，上一轮把它写成必走路线过早。

SQLite官方说明，CHECK约束在写入时检查，普通读取不重新检查，损坏数据库可能读出违反约束的数据；json_valid也只回答JSON格式是否合法。[SQLite约束](https://www.sqlite.org/lang_createtable.html#constraint_enforcement)、[JSON函数](https://www.sqlite.org/json1.html#the_json_valid_function)。

Kafka Compaction保留现存记录原offset与顺序，并按key保留最终状态；这不是“用原opId修好历史坏账”的直接保证。[Kafka设计文档](https://kafka.apache.org/41/design/design/#log-compaction)。Raft原文要求状态机识别已经执行的客户端序号并返回已有结果，不能用该论文为NativeSync缺失的重发布语义背书。[Raft论文第8节](https://raft.github.io/raft.pdf)。

## 2. 性能拆分与条件批量原型

`tests/fixtures/predicateBatchPrototype.cjs`仅供实验，产品代码没有引用。它按全部六项现有守卫和patch分组，使用`IS ?`保留NULL语义，ID每1000个分块，每块严格核对changes；所有组在同一个事务里，后组失效会回滚先组，不会半成功。重复ID拒绝。不用散列相等代替实际前置条件比较。

36种状态/标记组合加2100条同类行，与现有逐行应用结果相同。逐一变更state、kind、cancel_requested、request_dispatched、tool_started、pending_operation，旧计划均被拒绝且整个事务回滚。这是所测情形的证据，不是“100%并发安全”的普遍证明。

`tools/benchmark_restart_plans.cjs`复用上一轮最小schema、1KiB快照、临时SQLite WAL/FULL；每模式7次中位数，计入相应事务及读写成本，另外测读取、规划、分组、写入与提交。单位ms：

|行数/分布|原SQL|现有逐行|分组原型|组数/UPDATE数|
|---|---:|---:|---:|---:|
|4/同类|0.041|0.083|0.113|1/1|
|64/同类|0.155|0.558|0.548|1/1|
|10000/同类|27.020|91.839|79.273|1/10|
|10000/混合|25.390|80.272|82.159|36/36|

一万条同类数据的分组路径，各阶段中位数约为读取14.16、规划10.59、分组17.63、写入25.53、提交8.63；各阶段中位数相加不必等于总耗时中位数。独立纯内存重算约12.91ms；混合约10.52ms。分配带完整守卫的plan、读行和分组也有成本。这里的结果既不能给纯决策判死刑，也不能证明它不可能被进一步优化；只说明本原型没有兑现28ms预测。

保留全部守卫时，所构造混合状态产生36组；若pending_operation值各异，100行可产生100组。后者是守卫键范围的边界构造，不代表正常运行必有100个不同pending。当前真实调度上限64，不应为一万条压力数据直接增加生产复杂度。

## 3. 人工退出与现有原生探针

将上一轮独立文件副作用发生后进程exit78的场景，接上原会话的真实配对Cookie与HTTP路由：

1. 恢复后review_required、话题暂停；其他session无权解除。
2. 原session调用现有`/executions/:id/resolve`，action为`acknowledge_and_abandon_remaining`。
3. 父任务成为cancelled/reviewResolved，暂停解除，新显式请求可接受。
4. 旧attempts仍为1，独立文件只有一次效果；原started工具记录和REVIEW_REQUIRED原因保留，Journal没有因解除暂停新增内容。

PWA App.vue已有复选确认与按钮，明确提示不会重跑旧请求、取消AA或撤回副作用。本轮验收的是该HTTP路径与源码，不是手机浏览器或Windows UI现场验收；桌面端是否应补直接裁决入口可单独评估。

原生AA另有`registerNativeTaskProvider → queryNativeTask → nativeTasks.reconcile/result`。本轮用合成provider返回匹配原身份的终态证明，从unknown核对为completed、解除原生任务暂停并只读核验结果hash，派发计数仍为1。原生AA整链与归档回归也再次通过。这不意味着所有started工具都能查回，或者拿到AA终态就能补完任何中断父任务。

人工“确认外部已生效”应作为人工判断留下来源，不能伪造原生结算证据；强制重试也不能抹掉原调用身份。是否需要这两种新增动作，要看真实工具合同与产品需求，目前已有安全放弃出口。探针的I/O应在适配层，纯lifecycle可消费已经核验的观察，不应直接执行原生查询。

## 4. 生成器的定位

当前生成器是两个无import同步ESM模块的有限转换，导出名单手写，四个输出位置也手写；它不是通用模块打包器。后续模块若有依赖、重导出或更复杂构建要求，不应继续堆正则转换。保持packages为唯一维护源码、在发布组装目录产出部署副本，是合理方向；迁移时仍要验证CJS/ESM加载、宿主相对路径、PWA构建和安装依赖闭包。

第一轮报告已明确：新增generated文件需要更新部署清单；外部意见称“不动部署清单”不准确。当前生成检查通过，只能证明当前限定输入的产物一致，不能证明未来扩展都安全。本轮没有为了验证这个工程判断去替换现有构建链。
