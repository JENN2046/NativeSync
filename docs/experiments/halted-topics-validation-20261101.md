# haltedTopics：整话题暂扣与原位修复追赶实验

日期：2026-11-01。结论：**方向有条件可行，但“一个暂停列表加两类裸游标”不能直接满足五项安全条件。**
补足下述合同的独立原型取得13组定向证据；新增第14组反例又确认：合法但错误的归属字段可绕过当前逐行校验与该原型。
因此它还缺在线归属一致性核对，不能判为完全满足。这不是生产实现、完整应用验收或普遍安全证明。
现有84项载荷、产品协议、状态格式、数据库和运行中的开发配置均未修改；一万行分组原型未引入产品。

## 这次实际做了什么

原型在`experiments/halted-topics/`。服务端复用最终候选的真实CentralStore、消息／墓碑摘要及存储投影校验；
旧兼容反例调用真实旧Adapter的validatePullPage。新暂停控制、追赶端点与客户端双水位是独立实验代码。
实验从已离线重建的Linux代码底座加载模块，使用全新SQLite、合成消息、回环HTTP及真实子进程退出。
没有启动Electron／PWA／模型／工具／AA，没有读取真实聊天，没有把测试控制接口挂到产品。

fixture包含A话题的v1、v2、删除，与B话题健康更新交错；另覆盖修复期间A新增v3、两个独立客户端、
旧损坏在全局水位之后才被发现、重复熔断、响应丢失、跨来源范围拒绝、修复前后退出及历史行丢失。
共14个不同场景：先执行13组，再只运行新增归属反例1组；不运行历史联合矩阵或万行压测。

## 原样方案的反例

1. **修复后删掉服务端暂停标志，会遗忘旧缺口。** 客户端global已越过A缺口，重开若按新控制帧重建暂停表，A游标被清掉；后续只拉global之后的数据，A旧消息永远补不回来。
2. **原位修复也不能省掉每消息顺序检查。** 已有v2或墓碑的客户端被要求从较早seq补拉，若简单覆盖，收到v1后仍会短暂回退；在下一页到达前崩溃会留下旧状态。保持原seq只是必要条件，不是充分条件。
3. **旧端不会天然拒绝新字段。** 当前真实validatePullPage允许页面里有额外字段，也允许nextSeq越过未返回的事件；只增加haltedTopics而不协商，会让旧端丢掉缺口。
4. **当前投影正确不等于历史完整。** 删除早期v1 Journal后，最新墓碑与messages仍一致；仅检查当前投影会误以为完整。实验用修复时固定的前缀摘要检出丢行，拒绝释放追赶。
5. **合法字段不证明正确归属。** 在合成库中把A的seq1 owner_id改成已有foreign话题的合法owner，保留正文和内容hash。
   真实CentralStore.pull在仅授权foreign的范围中返回A原正文，原型也未产生haltedTopics。逐行语法／内容摘要不绑定原接受归属。
   随后复用已有只读检查器，报出1项`JOURNAL_PROJECTION_INVALID`；已有跨表核对能发现此反例，在线拉取和原型尚未接入。
   这不是现有资料库事件，不代表应直接新增签名账本；先核对既有引用校验如何进入在线路径。

此前“旧版本用新seq重发布”的反例仍成立。本实验不分配新的修复seq、不改原applied_ops回执、不把未知内容变成墓碑；
修复仅恢复可信原字节，不允许用客户端自报的digest把任意新字节认证成历史真相。

## 补强后的最小实验合同

```text
globalCursor = 已处理的全局扫描窗口末尾，不能表示每话题完整
haltedTopicCursors[topic] = {
    generation, cursor, state: halted | recovering | complete
}
```

暂停项需要稳定代次，防止同一话题第二次损坏时把旧完成回执误用于新暂停。complete记录保留为已追赶代次证明，
不是从map里马上删除。当前已观察的head只用于“是否追上本轮观测头部”的显示，不能替代任何接受或应用水位。
晚发现的旧坏行可以把该话题追赶起点拉低；global不回退，已更新消息也不回退。

服务端发现坏行时先耐久记录暂停，再发可推进健康话题的页面；同页整个坏话题都过滤。页边界之前已经成功应用的好数据不撤回，
而是标记该话题尚不完整。新暂停起点取客户端原global与firstUnsafeSeq之前的安全下界；两个客户端保留各自的下界。
本实验事务内的Journal插入守卫同时阻止绕过push包装的写入，健康话题仍可提交。

原位恢复使用事前健康时登记的备份摘要，原消息JSON、seq、hash、元数据、墓碑及当前投影一起核验。
“修复完成”与修复写入同一个SQLite事务。固定修复前缀摘要和head，追赶前再核验该前缀，避免旧历史被删后误报完整。
Journal必须保留到所有相关追赶完成；本原型保留Journal和代次记录，不实现GC。无可信副本或投影不一致时继续暂停。

追赶只读取 `(topicCursor, globalCursor]` 内的原Journal序列，分批推进话题水位；
所有页完成且代次、窗口和修复证明一致后，原子标为complete，之后由global路径接手。
若全局轮询已在网络请求间前进，旧追赶页不负责交接，必须按新窗口重新取页。

## 恢复与信任边界

客户端实验SQLite把消息物化、双水位与状态放在同一事务，服务端测试使用WAL／FULL及实际进程退出。
这证明所构造事务边界的进程重开行为，不证明宿主JSON文件、多存储提交或断电行为。
协议假定可核实的话题路由身份和可信修复来源；已知无法归属的损坏整体拒绝，不能宣称任意owner字段或整库损坏也可安全继续。
语法仍有效且恶意重写了所有一致性信息的内容，不在本实验可识别的存储故障模型内。

实验HTTP只模拟授权范围和能力协商，不替代生产Bearer／Cookie／Source绑定。接入产品时必须复用现有授权，
不能让请求正文自行宣布“属于此来源”或“已经修复”。模型调用、已有工具／AA恢复并未新增验收。

## 后续决定

可以保留这条路线作为可用性候选；它目前尚不完整，当前产品仍保持原有损坏失败关闭行为。
下一步先界定可信归属证据并复用现有跨表核对；无法可靠归属时必须全局失败关闭，不能按可疑owner错误隔离后继续。
若批准产品化，先单独制定同步能力／响应、客户端状态迁移、JSON／收件页恢复、暂停时写入与执行出口、PWA完整性提示、
范围变更及Journal留存的接线计划，再做对应整机中断验证。现有Source全量候选与回退合同不自动覆盖这些新语义。
