# Windows 真实历史兼容施工修订

2026-11-03。升级和同一 Source 扩围已经实际成功；32 个话题中29个历史就绪，剩余三个被实际合法数据的边界阻塞。此计划尚未实施，不把它混入已经批准的 sourceCatalog.js 单文件修复。

现场备份包含809条原生消息，808条可以按现有合同规范化，另1条包含63个桌面工作区活引用；其无普通附件内容哈希是原生设计，不是SQLite损坏。所有原消息在Windows仍保留，808条原身份/内容摘要全匹配，另1条原始JSON保持。现有原生引用内还保存约6.15MB历史提取文本；本轮没有读取实时工作区文件。

两条长文本的正文约2.80MB、1.09MB，序列化操作约2.97MB、1.12MB，超过现有1MiB操作上限；部分较小长文本也遇到8秒传输超时。group 的现有引用不能通过当前“必须有SHA256的普通附件”规范化，因此整个话题不能完成。这些问题无法靠换opId、清空错误、恢复旧state或等待解决。

1. **大消息先采用最小有界调整。** 优先验证同步单操作上限4MiB与仅用于源导入大载荷/大响应的60秒超时，核对实际网关、服务端和客户端三处约束。其他目录批次、元数据、附件单文件20MiB和交互请求限制继续保留。消息id、内容、哈希和原opId不变，不截断正文。暂不新增分块任务系统；若有界调整仍不足，再说明具体证据与代价。
2. **活引用作为明确的只读引用兼容。** 复用原生 workspaceRef 的身份和引用结构，在共享同步元数据中增加可识别的桌面引用表示。保留原消息正文、普通附件和引用；Windows原生历史里的63个引用及历史提取文本保持，不重写成假文件哈希。不读取当前工作区，也不重新抓取资料库。手机明确显示“桌面活引用，原件/提取内容尚未同步”，不能作为附件完成或当前工作区已可用的证明。本轮不另建历史快照/CAS机制；若用户要求手机读取这6.15MB提取文本，需另明确范围。
3. **新旧读取者显式兼容。** 引用表示属于共享合同扩展，需要能力声明/协商；旧读取者不能静默忽略引用。已有普通消息、原件附件、Source范围、Journal和回执规则保持。拟不增加SQLite迁移或新state版本；若做不到，先另行说明影响。投影覆盖首次导入、后续新增/编辑及远端落盘，不能仅让首导通过而删掉本机原生引用。仍依赖动态桌面上下文的会话继续明确不可手机续聊，不改变全局规则或Agent映射。
4. **普通附件按项处理不支持类型。** 已有.ps1上传被服务端现有类型检测拒绝，当前客户端却中断整个附件轮次，挡住后续允许的文件。修正为逐项保留明确原因并继续支持文件，不把脚本伪装成其他类型，也不自动扩大格式白名单。先核对余下未就绪引用分别属于话题未完成、类型不支持还是传输失败。
5. **验证只针对真实缺口。** 在本机合成数据中验证大消息边界与超时、接受后响应丢失仍按原操作接受一次；验证63个只读引用不会触发工作区文件读取，正文/引用/原件不丢，旧客户端明确拒绝不支持的表示。新合同涉及归属时保留跨来源拒绝。最终在Windows只恢复失败三个话题，再核对全局身份与数据保留，不重跑历史大矩阵。

实际追加安装前另出精确变更清单。最终结果仍按历史、普通附件、只读引用和不可续聊原因分别报告：29/32不是全量完成；63个桌面引用不计为普通原件已同步。现有32个话题及未来发现仍属于已接受的full Source，不撤回范围、数据库、游标或已接受消息。

建议先正常退出Windows VCPChat保留断点，停止对已知超限请求的重复尝试。当前有69条已耐久接收但受未完成话题阻挡的Inbox记录，应原样保留；正常关闭会等待当前工作，不清理Inbox或重置游标。生产服务与Linux来源可继续保留；本轮不生成扩大旧手机权限的配对。
